# Food Saver — Project Overview

Food Saver (`foodsaver` package) is a Flutter app for cutting household food waste. It tracks what is in the fridge and when it expires, warns before food goes off, manages shopping lists, lets users donate food that is about to expire, and includes a small rule-based assistant. Data is stored in Cloud Firestore when Firebase is configured, and in memory otherwise.

This file describes how the code is organised and how the UI is built. For the feature list of each team member's module (the *cahier des charges* mapping), see [README.md](README.md).

## 1. Tech stack

| Area | Choice |
| --- | --- |
| Framework | Flutter, Dart SDK `^3.13.5`, Material 3 |
| State management | Plain `ChangeNotifier` singletons + `ListenableBuilder` (no Provider / Riverpod / Bloc) |
| Navigation | Imperative `Navigator` + `MaterialPageRoute` (no named routes, no go_router) |
| Backend | Firebase: `firebase_core`, `cloud_firestore`, `firebase_auth` (project `foodsaver-83ca2`) |
| Images | `image_picker` (profile photo, stored as base64 in Firestore) |
| Notifications | `flutter_local_notifications` + `timezone` (local scheduling, no server) |
| Animations | `lottie` (`assets/animations/food_saver.json`) |
| Lints | `flutter_lints` (default rule set, platform folders excluded) |
| Dev tooling | `flutter_launcher_icons`; `tool/generate_app_icon.dart` draws the icon with the `image` package |

Target platforms: Android, iOS, web, Windows, macOS, Linux. Phone notifications only work on Android and iOS; on other platforms the notification service does nothing.

## 3. Architecture

### 3.1 Startup

[lib/main.dart](lib/main.dart):

1. `FirebaseSetup.init()` tries `Firebase.initializeApp`. On success `FirebaseSetup.isReady = true`; on failure (no config, tests) it logs the error and the app runs with in-memory data.
2. `NotificationRepository.instance.pushHandler` is set to `NotificationService.instance.showNow`, so donation events also appear as phone notifications.
3. `NotificationService.instance.init(FridgeRepository.instance)` starts without being awaited. It requests permission, then listens to the fridge and re-schedules the expiry alerts every time the fridge changes.
4. `runApp(const FoodSaverApp())` → `SplashScreen` → Home (signed in) or `WelcomeScreen` (signed out).

### 3.2 Repositories (state)

Every feature with data has a **repository that extends `ChangeNotifier`** and is exposed as a singleton:

```dart
static final FridgeRepository instance = FridgeRepository(
  remote: FirebaseSetup.isReady ? FridgeFirestore() : null,
);
```

- **In memory is the source of truth for the UI.** Each change updates the in-memory list, calls `notifyListeners()`, and then writes to Firestore in the background (`_sync(() => remote!.saveItem(item))`, with errors caught and logged). The UI updates straight away and doesn't wait for the network.
- **`remote` is nullable.** With `remote == null` (tests, no Firebase) the repository can seed sample data (`seed: true`), so the app always has something to show.
- **Real-time sync:** the fridge subscribes to `fridge_items` snapshots, so a change on one phone shows up on the others. `isLoading` stays true until the first snapshot arrives.
- **Testability:** repositories accept an injectable `clock` (`DateTime Function()`) and `remote`. Screens take an optional `repository` parameter that defaults to `.instance`:
  ```dart
  const FridgeScreen({super.key, this.repository}); // defaults to FridgeRepository.instance
  ```

### 3.3 Persistence classes (`*Firestore`)

Each `*Firestore` class wraps one part of the database and holds top-level `xToMap` / `xFromMap` conversion functions. Categories are stored **by name only**; their icon and colour come from the app. Paths:

| Path | Content |
| --- | --- |
| `users/{userId}` | profile (`displayName`, `email`, `photo`, `createdAt`, `settings`), custom food/shopping categories, selected shopping list, read notification ids |
| `users/{userId}/fridge_items/{id}` | one document per food |
| `users/{userId}/fridge_history/{id}` | consumed / wasted events (stats) |
| `users/{userId}/shopping_lists/{listId}` | one document per list, items embedded as an array |
| `users/{userId}/notifications/{id}` | donation events |
| `donations/{donationId}` | shared between all users, requests embedded |

`userId` comes from `CurrentUser.uid` ([lib/core/session/current_user.dart](lib/core/session/current_user.dart)): the signed-in account, bound by `SessionBinder`. Each repository has `connect()` and `clear()` so accounts never see each other data. Without a bound user (tests) it is the fixed `demo-user`.

### 3.4 How the modules connect

```
            FridgeRepository  ◄──── single source of truth for expiry dates
            │   │   │   │
            │   │   │   └──► NotificationService (schedules 7d / 3d / 0d alerts at 09:00)
            │   │   └──────► expiry_alerts.dart ─► Home "Expiring soon", ExpiringSoonScreen, NotificationsScreen
            │   └──────────► DonationRepository (donating removes quantity from the fridge; cancelling puts it back)
            └──────────────► ChatbotEngine (also reads ShoppingList + Donation repositories)

DonationRepository ──► NotificationRepository ──► pushHandler ──► NotificationService.showNow
```

Expiry alerts are never stored. They are recalculated from `FoodItem.expiryDate` each time.

## 4. UI

### 4.1 Navigation flow

```
SplashScreen ──► WelcomeScreen ──"Get Started"──► LoginScreen ──signIn──► FoodSaverHomePage
                        └──"Create account"──► RegisterScreen ──signUp──► FoodSaverHomePage
                                                                                 │
     bottom NavigationBar: Home · Fridge · List · Profile                        │
     quick-action cards: Fridge, Recipes, Donations, Assistant                   │
     bell icon (unread badge) ──► NotificationsScreen                            │
     "Expiring soon" card ──► ExpiringSoonScreen / FoodDetailsScreen ◄───────────┘
```

- There is **no shell scaffold or `IndexedStack`**. Each main screen (Home, Fridge, List, Profile) builds its own `NavigationBar` with a local `_selectedIndex`. Home *pushes* the tab screens; the tab screens switch to each other with `pushReplacement`.
- Form screens return a result through `Navigator.push<String>(...)` (for example the saved name or a message), and the calling screen shows it with `showAppSnackBar`.
- The login has no logic yet: "Log In" goes straight to Home, and "Forgot password" / "Sign up" do nothing.

### 4.2 Theme and visual language

Set in [lib/app.dart](lib/app.dart):

```dart
ColorScheme.fromSeed(
  seedColor: Color(0xFF4CAF50),
  primary:   Color(0xFF2E7D32),   // dark green: buttons, icons, links
  secondary: Color(0xFFFFC107),   // amber
  surface:   Color(0xFFF5F9F3),   // pale green-white background
)
useMaterial3: true
```

In practice the screens use **hard-coded colours** rather than `Theme.of(context)`:

| Role | Value |
| --- | --- |
| Primary text | `0xFF1B1B1B` |
| Secondary text | `Colors.black54` |
| Brand green | `0xFF2E7D32` (gradient `0xFF1B5E20 → 0xFF4CAF50` on hero cards) |
| Card background | `Colors.white` on the `0xFFF5F9F3` scaffold |
| Pastel accents (icon tiles) | teal `0xFFB2DFDB`, yellow `0xFFFFE082`, green `0xFFC8E6C9`, blue `0xFFBBDEFB` |
| Alert / badge | orange `0xFFE65100` |

Common patterns across the screens:

- **Rounded white cards**: `Container` + `BoxDecoration(color: white, borderRadius: 20–28)`, sometimes with a soft `BoxShadow` (`0x0F000000`, blur 12).
- **Large bold titles** (26–30 px) next to an `arrow_back_ios_new_rounded` back button (`ScreenHeader`).
- **Generous padding** (22–24 px horizontally), `SafeArea` + `SingleChildScrollView` / `ListView`.
- **Full-width pill buttons**: `ElevatedButton`, height 54–56, radius 18.
- **Filled text fields** with no border, a white fill and a green prefix icon.
- Material 3 components: `NavigationBar`, `Badge`, `SegmentedButton` (donation tabs), `ChoiceChip` (category filters), `Dismissible` (swipe to delete with Undo), `showModalBottomSheet` (category manager), floating `SnackBar`s, `FloatingActionButton` (add food).
- **Charts are built by hand** from widgets (`_WeekChart`, `_Bar` in `fridge_stats_screen.dart`). No chart package is used.
- Lottie animations have an `errorBuilder` that falls back to a Material icon.
- Text is in English. The chatbot also understands French keywords.

### 4.3 Shared widgets

[lib/shared/widgets/screen_header.dart](lib/shared/widgets/screen_header.dart) contains the cross-feature building blocks:

| Widget | Use |
| --- | --- |
| `ScreenHeader(title, actions)` | Back button + 28 px title row |
| `HeaderIconButton(icon, tooltip, onPressed)` | White rounded square icon button next to titles |
| `SectionTitle(text, trailing)` | 20 px section heading ("Expired", "Requests"…) |
| `EmptyCard(icon, message)` | Empty-state card |
| `showAppSnackBar(context, message)` | Floating, rounded snackbar that replaces the current one |

Widgets used by only one feature live in `features/<feature>/presentation/widgets/` (e.g. `FoodForm`, `ConsumeDialog`, `NameInputDialog`, `donation_widgets.dart`). Widgets used by only one screen are private classes (`_SummaryCard`, `_ActionCard`…) at the bottom of that screen's file.

### 4.4 Rebuilding on data changes

Screens use `ListenableBuilder(listenable: XRepository.instance, builder: ...)` around the parts that depend on repository data, e.g. the unread badge on the bell, the donation request count on the Donations card, and the live "Expiring soon" card on Home. `setState` is used only for local UI state such as search text, selected filter, sort order, tab index and form fields.

## 6. Running the app

```bash
flutter pub get
flutter run                 # choose a device
```

Firebase is already configured for project `foodsaver-83ca2` (`lib/firebase_options.dart`, `android/app/google-services.json`). To point the app at another project, run `firebase login` and then `flutterfire configure`, and create a Firestore database in the console. Without a working Firebase setup the app still runs, using in-memory sample data.

Android needs core library desugaring (already enabled in `android/app/build.gradle.kts`) and the `POST_NOTIFICATIONS` permission for alerts.

## 7. Known gaps / TODOs

- **Firestore rules are not deployed yet.** `firestore.rules` is the auth-based version with roles and is tested with the emulator (`firestore-tests/`, `npm test`), but deploying it breaks builds that still use `demo-user` and donor screens that accept requests. The rules in the Firebase project are still the open dev rules.
- **Roles are new**: restaurants can browse and request donations (`RestaurantDonationsTab`); the admin `AdminRequestsTab` lists pending requests and accepts or refuses them (donor notification and mark-collected are not built). Restaurants also have a Stock tab (their own fridge) and, like the admin, a History tab (`RequestHistoryTab`).
- **Placeholder content** on Home and Profile: "12 meals protected", the "Fridge: 7 items" / "Recipes: 3 ideas" cards, "128 meals saved", "92% impact", "18 saved recipes". The Recipes feature does not exist yet.
- **Navigation is duplicated** in each tab screen's `NavigationBar`. Home *pushes* tab screens, so the back stack grows. A single shell with an `IndexedStack` would fix both.
- **Colours are hard-coded** in every widget instead of read from the theme, so restyling or adding dark mode means editing many files.
- Beneficiaries for donations are simulated sample restaurants and charities, because beneficiary accounts don't exist yet.
